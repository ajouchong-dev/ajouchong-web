# 아주총 홈페이지 마스터 문서

이 문서는 아주대학교 총학생회 홈페이지를 처음 보는 사람도 화면 구조, 코드 흐름, 백엔드 API 연결, 관리자 운영 방식을 한 번에 이해할 수 있도록 정리한 상세 기술 설명서입니다. 여기서 말하는 "홈페이지"는 단순히 첫 화면(`/`)만이 아니라, 첫 화면에서 연결되는 사용자용 포털 전체와 그 뒤에서 동작하는 Spring Boot 백엔드까지 포함합니다.

작성 기준은 현재 작업 폴더의 실제 코드입니다.

- 프론트엔드 루트: `ajouchong-web`
- 백엔드 루트: `ajouchong`
- 첫 화면 컴포넌트: `ajouchong-web/src/pages/Main/index.js`
- 라우팅 중심 파일: `ajouchong-web/src/App.js`
- React 진입점: `ajouchong-web/src/index.js`
- 공통 헤더: `ajouchong-web/src/components/Header/Header.js`
- 공통 푸터: `ajouchong-web/src/components/Footer/index.js`
- 로그인 상태 관리: `ajouchong-web/src/contexts/AuthContext.js`
- 백엔드 인증 컨트롤러: `ajouchong/src/main/java/com/ajouchong/oauth/OAuthController.java`

## 1. 한 문장으로 이해하기

아주총 홈페이지는 아주대학교 총학생회의 소개, 공지, 소통 게시판, 회칙/회의록 자료, 학생복지, 축제 브랜드 ACENTIA, 링크허브를 한 곳에서 제공하고, 관리자는 같은 데이터를 관리자 페이지에서 수정할 수 있게 만든 React + Spring Boot 기반 학생회 포털입니다.

쉽게 말하면 다음 역할을 합니다.

```text
학생
  -> 홈페이지 접속
  -> 공지사항 확인
  -> Q&A 또는 안건 작성
  -> 회칙, 회의록, 감사자료 확인
  -> 제휴 혜택과 대여 물품 확인
  -> Google 로그인으로 개인 기능 사용

관리자
  -> Google 로그인
  -> ADMIN 권한 확인
  -> 공지, 제휴사업, 대여품, 링크, 회의록, 피드백 관리

백엔드
  -> 게시글/회원/자료/대여품 데이터를 DB에 저장
  -> 이미지와 파일은 S3 또는 정적 경로로 제공
  -> JWT 쿠키로 로그인 상태 검증
```

이 프로젝트에서 첫 화면(`/`)은 홍보용 랜딩 페이지만이 아닙니다. 홈페이지의 중심 허브 역할을 하며, 사용자가 필요한 기능으로 이동하도록 슬라이더, 퀵 링크, 대여 바로가기, 최신 공지 카드가 배치되어 있습니다.

## 2. 초보자 용어 사전

| 용어 | 쉬운 뜻 | 이 프로젝트에서의 예시 |
| --- | --- | --- |
| 프론트엔드 | 사용자가 브라우저에서 보는 화면 | `ajouchong-web/src/pages/Main/index.js` |
| 백엔드 | 화면 뒤에서 데이터 저장, 검증, 처리를 맡는 서버 | `ajouchong/src/main/java/com/ajouchong` |
| React | 화면을 컴포넌트 단위로 만드는 JavaScript 라이브러리 | `Main`, `Header`, `Footer` |
| 컴포넌트 | 화면 조각을 만드는 함수 단위 | `FeedbackWidget`, `ProtectedRoute` |
| 라우팅 | URL에 따라 어떤 페이지를 보여줄지 정하는 일 | `/news/notice` -> `Announcement` |
| state | 화면이 기억하는 현재 값 | `notices`, `loading`, `searchQuery` |
| hook | React에서 상태와 생명주기를 다루는 함수 | `useState`, `useEffect`, `useCallback`, `useMemo` |
| axios | 프론트엔드에서 백엔드 API를 호출하는 도구 | `apiClient.get('/api/notice')` |
| API | 프론트엔드가 백엔드에 데이터를 요청하는 주소 | `GET /api/rental/items` |
| DTO | API 요청/응답 데이터를 담는 객체 | `NoticePostResponseDto` |
| Entity | DB 테이블과 연결되는 Java 클래스 | `NoticePost`, `Member`, `RentalItem` |
| Repository | DB 조회/저장을 쉽게 해주는 계층 | `NoticePostRepository` |
| Service | 실제 비즈니스 규칙을 처리하는 계층 | `NoticePostService`, `RentalService` |
| JWT | 로그인한 사용자를 증명하는 토큰 | `accessToken`, `refreshToken` |
| Cookie | 브라우저에 저장되는 작은 데이터 | 백엔드가 설정하는 JWT 쿠키 |
| localStorage | 브라우저 내부 저장소 | `jwtToken`, `user` |
| CORS | 다른 도메인에서 API 호출을 허용하는 설정 | `SecurityConfig.corsConfigurationSource()` |
| SPA | 하나의 `index.html`에서 여러 페이지처럼 동작하는 앱 | React Router 구조 |
| Nginx | 빌드된 React 정적 파일을 서비스하는 웹 서버 | `nginx.conf`, `Dockerfile` |

## 6. 첫 진입점: `src/index.js`

파일: `ajouchong-web/src/index.js`

이 파일은 React 앱의 시작점입니다. 브라우저가 `public/index.html`을 열면 그 안의 `<div id="root"></div>`를 찾아 React 앱을 붙입니다.

핵심 구조는 다음과 같습니다.

```jsx
const clientId = process.env.REACT_APP_GOOGLE_CLIENT_ID;

const root = ReactDOM.createRoot(document.getElementById('root'));
root.render(
  <React.StrictMode>
    <GoogleOAuthProvider clientId={clientId}>
      <App />
    </GoogleOAuthProvider>
  </React.StrictMode>
);
```

초보자 관점에서 풀면 다음과 같습니다.

- `document.getElementById('root')`: React 화면을 넣을 HTML 위치를 찾습니다.
- `ReactDOM.createRoot(...).render(...)`: 그 위치에 React 앱을 그립니다.
- `React.StrictMode`: 개발 중 잠재 문제를 더 잘 찾도록 도와주는 React 도구입니다.
- `GoogleOAuthProvider`: 하위 컴포넌트에서 Google 로그인을 사용할 수 있도록 전체 앱을 감쌉니다.
- `clientId`: Google OAuth 클라이언트 ID입니다. `REACT_APP_GOOGLE_CLIENT_ID` 환경변수에서 가져옵니다.
- `<App />`: 실제 홈페이지 전체 라우팅과 공통 레이아웃을 담당하는 컴포넌트입니다.

즉, `index.js`는 화면 자체를 많이 만들지는 않지만, 앱 전체를 시작하고 Google 로그인 기능이 모든 페이지에서 동작하도록 준비합니다.

## 7. 공통 앱 구조: `src/App.js`

파일: `ajouchong-web/src/App.js`

`App.js`는 홈페이지 전체의 뼈대입니다. 모든 페이지가 공통으로 사용하는 Header, Footer, FeedbackWidget을 배치하고, URL에 따라 어떤 페이지를 보여줄지 정합니다.

핵심 구조는 다음과 같습니다.

```jsx
<AuthProvider>
  <Router>
    <div className="App">
      <Header />
      <div className="content">
        <Content />
      </div>
      <FeedbackWidget />
      <Footer />
    </div>
  </Router>
</AuthProvider>
```

각 요소의 역할은 다음과 같습니다.

| 요소 | 역할 |
| --- | --- |
| `AuthProvider` | 로그인 상태, 사용자 정보, 로그아웃, Google 로그인 함수를 전체 앱에 공급 |
| `Router` | 브라우저 URL을 읽고 React 페이지 전환을 처리 |
| `Header` | 상단 로고, 외부 링크, 메뉴, 로그인 버튼, 모바일 메뉴 |
| `Content` | 현재 URL에 맞는 실제 페이지를 렌더링 |
| `FeedbackWidget` | 우측 하단 퀵 메뉴와 의견 보내기 패널 |
| `Footer` | 주소, 이용약관, 개발자 정보, 저작권 |

`Content` 컴포넌트는 `useLocation()`으로 현재 경로를 읽습니다. 경로가 `/`가 아니면 Breadcrumb을 보여주고, 첫 화면에서는 Breadcrumb을 숨깁니다.

```jsx
const showBreadcrumb = location.pathname !== '/';
{showBreadcrumb && <Breadcrumb />}
```

## 20. 공지사항 데이터 로딩

홈 화면의 핵심 API 호출은 `fetchNotices`입니다.

```jsx
const response = await apiClient.get('/api/notice');
```

응답이 성공하면 다음 순서로 처리합니다.

1. `response.data.code === 1`인지 확인합니다.
2. `response.data.data`가 배열인지 확인합니다.
3. `npCreateTime` 기준으로 최신순 정렬합니다.
4. 앞에서 4개만 잘라냅니다.
5. `formatNoticeData`로 화면용 구조로 바꿉니다.
6. ID가 없는 항목은 제외합니다.
7. `setNotices(formattedNotices)`로 화면 state를 갱신합니다.

코드 흐름은 다음과 같습니다.

```text
GET /api/notice
  -> response.data.code 확인
  -> data 배열 확인
  -> 최신순 정렬
  -> 4개만 선택
  -> { id, title, content, image, date }로 변환
  -> notices state 저장
  -> 공지 카드 렌더링
```

백엔드 API 오류가 나면 화면은 멈추지 않고 콘솔에 오류를 남깁니다. 공지 카드 영역에는 `공지사항이 없습니다.` 문구가 보입니다.

## 21. 홈 화면 애니메이션과 `useEffect`

`Main/index.js`에는 `useEffect`가 두 개 있습니다.

첫 번째는 화면 요소가 보이는 순간 애니메이션 클래스를 붙이는 역할입니다.

```jsx
useEffect(() => {
  const elements = document.querySelectorAll('.more-link, .division-line, .card-title');

  const observer = new IntersectionObserver((entries) => {
    entries.forEach(entry => {
      if (entry.isIntersecting) {
        entry.target.classList.add('visible');
        observer.unobserve(entry.target);
      }
    });
  }, {
    rootMargin: '0px 0px -10% 0px',
    threshold: 0
  });

  elements.forEach(element => observer.observe(element));

  return () => observer.disconnect();
}, []);
```

이 코드는 브라우저의 `IntersectionObserver`를 사용합니다. 특정 요소가 화면 안으로 들어오면 `visible` 클래스를 붙이고, CSS transition으로 자연스럽게 나타나게 합니다.

두 번째는 공지사항 API를 호출합니다.

```jsx
useEffect(() => {
  fetchNotices();
}, [fetchNotices]);
```

이 코드는 `Main` 컴포넌트가 처음 렌더링될 때 최신 공지를 가져오도록 만듭니다.

## 23. API 호출 방식

const apiClient = axios.create({
  baseURL: process.env.REACT_APP_API_URL || 'https://api.ajouchong.com'

## 25. 로그인과 인증 구조

로그인 상태는 `AuthContext.js`가 관리합니다.

파일: `ajouchong-web/src/contexts/AuthContext.js`

### 25.1 앱 시작 시 로그인 상태 복구

처음 state는 `localStorage`에서 읽습니다.

```jsx
const token = localStorage.getItem("jwtToken");
const user = localStorage.getItem("user");
```

토큰이 있으면 `isAuthenticated`를 true로 시작하고, 이후 `/api/login/auth/info`를 호출해 실제 사용자 정보를 다시 확인합니다.

### 25.2 로그인 성공 흐름

로그인 버튼은 `Login` 컴포넌트에서 `useGoogleAuth`를 실행합니다.

```jsx
const signInWithGoogle = useGoogleAuth(navigate);
```

성공하면 다음 순서로 진행됩니다.

1. Google에서 `access_token`을 받습니다.
2. 프론트엔드가 Google userinfo API를 호출해 사용자 이름/이메일을 가져옵니다.
3. 프론트엔드가 백엔드 `/api/login/auth/oauth`로 Google accessToken을 보냅니다.
4. 백엔드가 Google 사용자 정보를 검증합니다.
5. 백엔드가 `Member`를 조회하거나 새로 만듭니다.
6. 이메일이 ADMIN allowlist에 있으면 `ADMIN`, 아니면 `STUDENT` 권한을 부여합니다.
7. 백엔드가 JWT accessToken과 refreshToken을 쿠키로 설정합니다.
8. 프론트엔드는 `localStorage`에 `jwtToken`, `user`를 저장합니다.
9. 로그인 후 `/profile`로 이동합니다.

### 25.3 관리자 접근

관리자 페이지는 두 번 보호됩니다.

프론트엔드에서는 `ProtectedRoute`가 먼저 확인합니다.

```jsx
if (!auth.isAuthenticated) {
  return <Navigate to="/" replace />;
}

if (requiredRole && auth.user?.role !== requiredRole) {
  return <Navigate to="/profile" replace />;
}
```

백엔드에서는 `SecurityConfig`가 `/api/admin/**`를 보호합니다.

```java
.requestMatchers("/api/admin/**").hasRole(MemberRole.ADMIN.name())
```

즉, 화면에서 숨기는 것만으로 끝나지 않고 서버에서도 관리자 권한을 검증합니다.

## 31. 관리자 페이지 운영 흐름

관리자는 `/admin`에 접속해 여러 데이터를 직접 관리합니다.

접근 조건은 다음과 같습니다.

1. Google 로그인 필요
2. 백엔드 Member role이 `ADMIN`이어야 함
3. 프론트엔드 `ProtectedRoute` 통과
4. 백엔드 `/api/admin/**` 권한 검사 통과

관리자 화면의 대표 작업 흐름은 다음과 같습니다.

```text
관리자 로그인
  -> /admin 이동
  -> NoticeManager에서 공지 등록
  -> 이미지가 있으면 FormData로 업로드
  -> POST /api/admin/notice
  -> NoticePostService가 DB와 S3 처리
  -> 학생 화면 / 또는 /news/notice 에 바로 반영
```

대여사업은 다음 흐름입니다.

```text
관리자
  -> RentalManager에서 품목 등록
  -> 이미지 업로드
  -> 총 수량/현재 수량 입력
  -> 학생 화면 /welfare/rental 에서 재고 확인
  -> 관리자 화면에서 대여 기록 생성 또는 재고 조정
```

회의록은 다음 흐름입니다.

```text
관리자
  -> ProceedingManager에서 카테고리 생성
  -> 회의록 파일 업로드
  -> 문서 제목, 회의일, 파일 URL 등록
  -> 학생 화면 /resources/proceeding 에서 열기/다운로드
```

## 34. 배포 구조

### 34.1 Vercel 배포

`vercel.json`은 React SPA 배포를 위한 설정입니다.

```json
{
  "rewrites": [
    {
      "source": "/(.*)",
      "destination": "/index.html"
    }
  ],
  "buildCommand": "npm run build",
  "outputDirectory": "build",
  "installCommand": "npm install"
}
```

`rewrites`가 중요한 이유는 React Router 때문입니다. 예를 들어 사용자가 `/news/notice`로 직접 접속하면 서버에는 실제 `/news/notice` 파일이 없습니다. 이때 Vercel이 `/index.html`을 내려주면 React Router가 브라우저에서 해당 페이지를 렌더링합니다.

### 34.2 Docker + Nginx 배포

`Dockerfile`은 두 단계로 되어 있습니다.

1. Node 이미지에서 `npm run build`로 React 앱을 빌드합니다.
2. Nginx 이미지에 빌드 결과를 복사해 정적 파일로 제공합니다.

```text
node:lts
  -> npm install
  -> npm run build
  -> /app/build 생성

nginx:1.21.0
  -> /usr/share/nginx/html 비우기
  -> build 결과 복사
  -> nginx.conf 적용
  -> 80 포트 노출
```

`nginx.conf`에서도 SPA 처리를 위해 다음 설정을 사용합니다.

```nginx
location / {
  try_files $uri /index.html;
}
```

### 34.3 백엔드 Docker Compose

`docker-compose.yml`에는 PostgreSQL과 백엔드 서비스가 정의되어 있습니다.

| 서비스 | 역할 |
| --- | --- |
| `database` | PostgreSQL 14.12 |
| `backend` | `ytnwjd/ajouchong-backend:latest` 이미지 |

백엔드는 `database` 서비스에 의존하고, 8080 포트를 외부에 노출합니다.

## 36. 자주 만나는 오류

### 36.1 첫 화면 공지사항이 비어 있음

확인할 것:

1. `REACT_APP_API_URL`이 올바른 백엔드 주소인지 확인합니다.
2. 브라우저 Network 탭에서 `GET /api/notice` 응답을 봅니다.
3. 응답의 `code`가 1인지 확인합니다.
4. `data`가 배열인지 확인합니다.
5. 각 공지에 `npTitle`, `npContent`, `npCreateTime`이 있는지 확인합니다.

### 36.2 공지 이미지만 깨짐

확인할 것:

1. `imageUrls[0]` 값이 실제 접근 가능한 URL인지 확인합니다.
2. 이미지가 S3에 존재하는지 확인합니다.
3. 브라우저에서 이미지 URL을 직접 열어봅니다.
4. fallback 이미지 `/images/main/achim_square.jpeg`가 존재하는지 확인합니다.

### 36.3 로그인이 안 됨

확인할 것:

1. `REACT_APP_GOOGLE_CLIENT_ID`가 설정되어 있는지 확인합니다.
2. Google OAuth 설정에서 허용 도메인이 맞는지 확인합니다.
3. 사용자의 이메일 도메인이 `ajou.ac.kr`인지 확인합니다.
4. `/api/login/auth/oauth` 요청이 성공하는지 확인합니다.
5. 백엔드 쿠키가 브라우저에 저장되는지 확인합니다.

### 36.4 관리자 페이지에 못 들어감

확인할 것:

1. 로그인한 사용자의 `role`이 `ADMIN`인지 확인합니다.
2. 해당 이메일이 `OAuthController`의 `ADMIN_EMAIL_ALLOWLIST`에 있는지 확인합니다.
3. `/api/login/auth/info` 응답이 최신 권한을 반환하는지 확인합니다.
4. 프론트엔드 localStorage의 `user`가 오래된 값이면 로그아웃 후 다시 로그인합니다.
5. 백엔드 `/api/admin/**` 응답이 401인지 403인지 확인합니다.

### 36.5 CORS 오류가 남

확인할 것:

1. 프론트엔드 도메인이 `SecurityConfig`의 `allowedOriginPatterns`에 있는지 확인합니다.
2. 쿠키 인증을 쓰는 요청은 `withCredentials: true`를 사용해야 합니다.
3. 백엔드 CORS 설정에서 `setAllowCredentials(true)`가 유지되어야 합니다.
4. HTTPS와 HTTP가 섞이지 않았는지 확인합니다.

### 36.6 대여사업 수량이 이상함

확인할 것:

1. `/api/rental/items` 응답의 `totalQuantity`, `currentQuantity` 값을 확인합니다.
2. 프론트엔드에서 `total`, `current`로 정상 변환되는지 확인합니다.
3. `currentQuantity`가 `totalQuantity`보다 커지지 않도록 관리자 입력을 검증해야 합니다.
4. 대여 기록 생성/반납 처리에서 재고 조정이 올바른지 `RentalService`를 확인합니다.

### 36.7 Kakao 지도가 안 뜸

확인할 것:

1. Kakao JavaScript SDK 키가 유효한지 확인합니다.
2. Kakao 개발자 콘솔에 현재 도메인이 등록되어 있는지 확인합니다.
3. 브라우저 콘솔에서 `window.kakao`가 존재하는지 확인합니다.

## 38. 코드 읽기 연습

### 38.1 `/`가 왜 메인 화면인가?

1. `src/index.js`가 `<App />`을 렌더링합니다.
2. `App.js` 안에 `<Router>`가 있습니다.
3. `Routes` 안에 `<Route path="/" element={<Main />} />`가 있습니다.
4. 그래서 브라우저 주소가 `/`이면 `Main` 컴포넌트가 보입니다.

### 38.2 메인 화면이 공지를 어디서 가져오나?

1. `Main/index.js`에서 `useEffect`가 실행됩니다.
2. `fetchNotices()`가 호출됩니다.
3. `apiClient.get('/api/notice')`가 실행됩니다.
4. 백엔드 `NoticePostUserController.getAllNoticePosts()`가 응답합니다.
5. 프론트엔드가 최신순으로 정렬하고 4개만 선택합니다.
6. `setNotices()`로 state를 바꾸면 공지 카드가 렌더링됩니다.

### 38.3 Q&A 글쓰기는 왜 로그인이 필요한가?

1. 사용자가 `글 작성하기`를 누릅니다.
2. `PostList.goToWritePage()`가 `/api/login/auth/info`를 호출합니다.
3. 로그인 정보가 있으면 글쓰기 페이지로 이동합니다.
4. 글쓰기 페이지도 처음 열릴 때 `checkLoginStatus()`를 실행합니다.
5. 실제 작성 API `/api/qna`도 백엔드에서 accessToken 쿠키를 확인합니다.
6. 즉 화면 이동과 서버 저장 단계에서 모두 로그인 여부를 확인합니다.

### 38.4 대여사업 화면은 어떻게 재고 상태를 계산하나?

1. `/api/rental/items`에서 대여품 목록을 가져옵니다.
2. 각 항목의 `totalQuantity`와 `currentQuantity`를 `total`, `current`로 바꿉니다.
3. `statusOf(current, total)`이 상태를 계산합니다.
4. 현재 수량이 0이면 `품절`입니다.
5. 현재 수량이 전체의 20% 이하이면 `임박`입니다.
6. 그 외에는 `가능`입니다.

### 38.5 관리자 페이지는 어디서 막히나?

1. `/admin` 라우트는 `ProtectedRoute requiredRole="ADMIN"`으로 감싸져 있습니다.
2. 로그인하지 않았으면 `/`로 이동합니다.
3. 로그인했지만 권한이 ADMIN이 아니면 `/profile`로 이동합니다.
4. 프론트엔드 검사를 통과해도 백엔드 `/api/admin/**`는 Spring Security가 다시 검사합니다.

## 39. 개선 포인트

현재 구조는 동작을 이해하기 쉽지만, 유지보수 관점에서 개선할 수 있는 부분도 있습니다.

| 개선 항목 | 현재 상태 | 개선 방향 |
| --- | --- | --- |
| API 클라이언트 | 각 파일에서 axios 인스턴스 반복 생성 | `src/api/client.js`로 공통화 |
| 에러 처리 | 페이지별 `console.error` 중심 | 공통 에러 메시지/토스트 패턴 도입 |
| 로딩 상태 | 일부 페이지에만 있음 | 모든 API 페이지에 loading/error/empty 상태 통일 |
| 공지 ID 처리 | `nPost_id`, `npost_id`, `id`를 모두 확인 | 백엔드 DTO 필드명을 하나로 통일 |
| 인증 저장 | JWT 쿠키와 localStorage 병행 | 보안 정책을 정하고 저장 위치 정리 |
| 관리자 allowlist | 코드에 이메일 직접 작성 | DB 또는 환경변수 기반 관리 |
| Kakao App Key | 코드에 직접 작성 | 환경변수로 이동 |
| 접근성 | 일부 버튼/링크 aria 존재 | 모든 이미지 alt, 버튼 label 점검 |
| 테스트 | 기본 CRA 테스트만 있음 | 주요 페이지 렌더링/권한/필터 테스트 추가 |

## 40. 핵심 요약

아주총 홈페이지는 `ajouchong-web`의 React 앱과 `ajouchong`의 Spring Boot API가 함께 동작하는 학생회 포털입니다.

가장 중요한 파일은 다음 네 개입니다.

- `src/index.js`: React 앱 시작점과 Google OAuth Provider 설정
- `src/App.js`: 전체 라우팅과 공통 레이아웃
- `src/pages/Main/index.js`: 첫 화면 슬라이더, 퀵 링크, 대여 바로가기, 최신 공지
- `src/contexts/AuthContext.js`: 로그인, 로그아웃, 사용자 정보, Google OAuth 연동

첫 화면은 다음 순서로 동작합니다.

```text
브라우저에서 / 접속
  -> App.js가 Main 렌더링
  -> 히어로 슬라이더 표시
  -> 퀵 링크 표시
  -> GET /api/notice 호출
  -> 최신 공지 4개 표시
```

로그인은 다음 순서로 동작합니다.

```text
Login 클릭
  -> Google OAuth
  -> 백엔드 /api/login/auth/oauth
  -> Member 조회/생성
  -> JWT 쿠키 설정
  -> localStorage 저장
  -> Profile 또는 Admin 접근
```

관리자 운영은 다음 흐름입니다.

```text
ADMIN 로그인
  -> /admin
  -> 공지/제휴/대여/링크/회의록/피드백 관리
  -> 백엔드 /api/admin/**
  -> DB 또는 S3 갱신
  -> 사용자 페이지에 반영
```

따라서 이 홈페이지를 이해할 때는 "화면 파일만 보는 것"보다, `React 화면 -> axios API -> Spring Controller -> Service -> Entity/DB -> 다시 화면 갱신` 흐름을 따라가면 전체 구조가 가장 빠르게 잡힙니다.
